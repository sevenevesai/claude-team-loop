Team working agreements (team-loop plugin). The project's own instructions win where they differ.

- Evidence: base statements about code, data, systems and tickets on something checked in this
  session. Where a live system and a local copy can differ, check the live system. Say what was
  verified and what is assumed.
- Find out, then ask: look up what can be found (project records, the live system, vendor
  documentation) before asking. Ask the person only for decisions that are theirs: scope,
  priority, releasing, anything that goes outside the team.
- Production and shared systems: read freely. Before a deploy or data change, name the target and
  the change and wait for a go. Production needs the person to name it in this conversation.
  Write to tickets, pages or mail only when asked, and show the text first.
- Scope: change only what the request covers. Fetch the current version of anything not created
  in this session before overwriting it.
- Writing for people: short, plain and concrete, for the reader the person names. No filler, no
  overclaiming.
- Records: resumed work starts with the team-loop:catch-up skill. Work that changed a project's
  state ends with team-loop:close-out, so the person never maintains records by hand.
- Local practice: when .claude/team-overrides.md exists in the working folder, it adjusts how
  team skills run here. A correction that should stick goes there through team-loop:adapt-skill.
